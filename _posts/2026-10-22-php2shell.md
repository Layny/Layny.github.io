Mardi soir, l'équipe sécurité de PHP a prévenu qu'une mise à jour d'urgence sortirait le lendemain à 16h (heure de Paris) pour corriger **deux failles critiques**, toutes les deux notées 9.2/10 en CVSS v4.0. Sans aucun détail, ce qui est rare pour PHP.

L'éditeur a communiqué aussi vite dû à la fuite sur Hacker News et qu'une vidéo de démonstration circulait. Les chercheurs ont baptisé les failles **php2shell**, et le nom parle de lui même : un attaquant distant récupère un shell sur le serveur et sans avoir besoin d'une faille dans l'application.

## Chronologie rapide

- **Août** : les failles sont signalées à PHP par des chercheurs de Calif, de Wiz (Google) et d'OpenAI.
- **17/10** : Amazon repère sur ses honeypots une tentative d'exploitation, quatre jours avant la divulgation.
- **20/10** : la fuite sur Hacker News, puis l'annonce de PHP. Le CERT-EU publie son avis.
- **21/10** : les attaques s'intensifient avant le patch, qui sort dans l'après-midi. CISA, NCSC, NSA et FBI appellent à patcher vite, voire à couper les serveurs exposés.
- **22/10** : le CERT-FR précise avoir connaissance de preuves de concept, et ASEC analyse la vague de dépôts « php2shell » apparus sur GitHub depuis la veille.

## Les deux failles

L'avis officiel, publié avec le patch, décrit deux bugs distincts.

**CVE-2026-109618** ([GHSA-w8hw-w9fx-j79w](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w)) 

**CVE-2026-109619** ([GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp))

L'avis parle aussi de **divulgation de mémoire**. Selon les chercheurs, un attaquant peut lire des morceaux de la mémoire d'un worker PHP, qui peut contenir des mots de passe, des jetons ou des clés d'API issus d'autres requêtes (JFrog parle d'une fuite façon Heartbleed). Il est donc pas nécessaire d'éxecuter la moindre commande.


### Versions concernées

| Branche | Vulnérable | Corrigée |
|---|---|---|
| 8.5 | jusqu'à 8.5.11 | 8.5.12-1 |
| 8.4 | jusqu'à 8.4.26 | 8.4.27-1 |
| 8.3 | jusqu'à 8.3.35 | 8.3.36-1 |
| 8.2 | jusqu'à 8.2.34 | 8.2.35-1 |
| 8.1 et plus ancien | oui (5.x, 7.x, 8.0, 8.1 selon le CERT-FR) | pas de version officielle, correctifs source minimaux publiés par PHP pour 7.4, 8.0 et 8.1 |

Le niveau de risque dépend de la façon dont PHP est branché au serveur web :

- **Apache + mod_php** : le pire cas. La RCE complète est démontrée pour les deux CVE, sans authentification.
- **PHP-FPM** : exposé aussi, mais plus conditionnel. La RCE via CVE-2026-109619 a été validée, et il faut une opération applicative adaptée. Pour CVE-2026-109618, aucun exploit FPM complet n'a été démontré.
- **PHP 8.5** : c'est là que le cas le plus solide a été démontré, via l'option `fatal_error_backtraces`.


### Côté autorités

En France, le CERT-FR recommande d'isoler les équipements affectés puis de migrer vers une version maintenue ([alerte CERTFR-2026-ALE-014](https://cert.cyber.gouv.fr/alerte/CERTFR-2026-ALE-014/)). D'après l'Anssi citée par ActuIA, plus de 600 000 serveurs PHP sont visibles sur l'Internet français, et Infosecurity indique que plusieurs administrations françaises ont coupé leurs sites le temps de patcher. Côté CISA, la consigne est de patcher immédiatement ou, à défaut, de mettre le système hors ligne.

## Et les PoC ?

Des dizaines de dépôts « php2shell » sont apparus sur GitHub quelques heures après le patch. 
Les analyses publiées avant le patch, qui partaient souvent de l'hypothèse « tout vient de Session Upload Progress », sont à lire avec prudence maintenant que l'avis officiel a rebattu les cartes.

Si vous voulez tester quand même : VM jetable, sans réseau sortant, sans clés ni credentials dessus, lecture complète du code avant de l'exécuter, et uniquement contre votre propre lab.

## Que faire

### 1. Faire l'inventaire

Avant tout, il faut savoir où tourne PHP : serveurs web, conteneurs, vieilles VM oubliées, appliances. Pensez aussi aux logiciels qui embarquent leur propre PHP (FrankenPHP, panneaux d'hébergement, outils de dev comme XAMPP ou MAMP) : `apt` ne les met pas à jour.

Petit piège classique : `php -v` donne la version du PHP en ligne de commande, pas forcément celle qui sert le site (PHP-FPM ou module Apache). Il faut regarder la bonne commande :

```bash
# Version de PHP-FPM (celle qui sert réellement les pages), adapter le numéro
php-fpm8.4 -v

# Paquets PHP installés (Debian/Ubuntu)
dpkg -l | grep -E 'php[0-9.]*-fpm|libapache2-mod-php'

# Version de PHP dans chaque conteneur Docker actif
for c in $(docker ps -q); do docker exec "$c" php -v 2>/dev/null | head -1; done
```

### 2. Patcher

Concernant les mises à jours, il est recommandé vivement de passer à la dernière version (voir le tableau précédent) que l'on peut trouver directement via le site ([PHP](https://www.php.net/archive/2026.php#2026-10-21-5): 

Exemple de upgrade : 
```bash
# Debian/Ubuntu, adapter la version
sudo apt update
sudo apt install --only-upgrade 'php8.4*' libapache2-mod-php8.4
sudo systemctl restart php8.4-fpm   # ou apache2 pour mod_php
```
La mis à jour est également déjà déployé dans les repository de distribution différentes, un simple `sudo apt upgrade` peut alors suffir.


### 3. Si on ne peut pas patcher tout de suite

PHP est très clair : seule la mise à jour règle le problème. Les mesures qui suivent ne ferment que certains chemins.

**Contre CVE-2026-109619**, on désactive Session Upload Progress (les éventuelles barres de progression d'upload ne marcheront plus). Sous Debian/Ubuntu, le plus propre est un fichier dédié dans `conf.d`, qui survit aux mises à jour :

```bash
# PHP-FPM
echo 'session.upload_progress.enabled = Off' | sudo tee /etc/php/8.4/fpm/conf.d/99-php2shell.ini
sudo systemctl restart php8.4-fpm

# Vérifier côté serveur web (et pas seulement côté CLI)
php-fpm8.4 -i | grep upload_progress.enabled
```

Avec Apache + mod_php, même principe dans `/etc/php/8.4/apache2/conf.d/` puis `systemctl restart apache2`. Pour l'image Docker officielle, le fichier va dans `/usr/local/etc/php/conf.d/`. La directive doit être posée dans le `php.ini`, le pool FPM ou la config du serveur : `ini_set()` et `.user.ini` arrivent trop tard.

**Contre CVE-2026-109618**, PHP propose :

- `memory_limit=-1`, imposé via `php_admin_value` pour que les applis ne puissent pas le remettre. Attention, ça retire tout plafond côté PHP.
- Un `post_max_size` bas (8M sans upload, 32M avec) et des limites de taille de requête sur un reverse proxy.

Là encore, ce n'est pas une protection complète : un échec d'allocation plus bas niveau peut quand même atteindre le chemin vulnérable.


### 4. Chercher des traces

⚠️ L'exploitation laisse très peu de traces. D'après CrowdStrike, les workers restent stables, les réponses sont en HTTP 200 et les logs applicatifs ne montrent rien, puisqu'aucun code applicatif ne s'est exécuté. 
La seule trace côté serveur peut être une unique erreur de limite mémoire dans le log d'erreurs du serveur web.
L'avis officiel le rappelle aussi : **ne rien trouver dans les logs ne prouve pas qu'on est sain**.

**Les erreurs mémoire, et les crashs en second.** On cherche des *Allowed memory size exhausted* et des *Maximum execution time exceeded*, même isolés, à corréler avec des `POST` multipart volumineux ou inhabituels dans les access logs. Les crashs de workers (signal 11) sont un signal supplémentaire, mais pas le principal.

```bash
grep -Ei 'Allowed memory size|Maximum execution time' /var/log/php*-fpm.log /var/log/apache2/error.log
grep -Ei 'SIGSEGV|signal 11|Segmentation fault' /var/log/php*-fpm.log /var/log/apache2/error.log
grep -i 'php2shell-scan' /var/log/nginx/access.log* /var/log/apache2/access.log*
```

**Des fichiers PHP apparus récemment**, typiquement un webshell pour garder l'accès (backdoor par exemple):

```bash
find /var/www -name '*.php' -newermt '2026-10-17' -ls
ls -la /tmp /var/tmp /dev/shm
```

(La date est celle de la première tentative connue, adaptez-la à votre exposition.)

**Le serveur web qui lance des commandes système.** Un serveur PHP qui exécute `bash`, `curl` ou `wget`, c'est rarement normal. Dans un EDR ou un SIEM, une règle « parent `php-fpm` ou `apache2 `sh` / `bash` / `curl` ... » est un moyen de repérer une RCE. Sans EDR, auditd peut faire le job :

```bash
# Tracer toutes les commandes lancées par www-data (uid 33 pour Debian)
sudo auditctl -a always,exit -F arch=b64 -S execve -F uid=33 -k php2shell
sudo ausearch -k php2shell -i | grep -E 'comm=(sh|bash|curl|wget|nc)'
```

Et si l'attaquant n'a fait que lire la mémoire, il n'y aura ni shell ni fichier. Pour un serveur exposé qui n'était pas patché pendant la fenêtre d'attaque, le plus prudent est de renouveler les secrets qui transitent par PHP (clés d'API, jetons, mots de passe de base de données).

> ⚠️ Si vous trouvez quelque chose : isolez le serveur avant de le patcher pour garder les traces, et considérez que tous les secrets lisibles par le site sont compromis (base de données, clés d'API, `.env`, `wp-config.php`, comptes de service).

## Bilan

Côté offensif, c'est un accès initial très intéressant : un serveur web en DMZ mal cloisonné avec un compte de service AD dans un fichier de conf, et c'est le SI interne qui peut être à la portée.

À court terme : inventaire, patch avec redémarrage (et vérification qu'aucun process ne tourne sur l'ancien binaire), mitigations là où c'est impossible, chasse aux traces, et renouvellement des secrets si le doute est permis. À plus long terme, ça rappelle que laisser traîner une version fin de vie, c'est juste attendre la prochaine CVE.
